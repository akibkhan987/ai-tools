# TrailBlazer API – Design and Development

## 1. Application area and dataset

TrailBlazer helps walkers find hikes that suit them (where they are, how fit they are, whether they have a dog or need parking) and share experience through reviews. A single back end could serve a web front end, a mobile app used at the trailhead, or a stats dashboard.

**Dataset.** `seed/trails_source.py` contains 45 real walking routes across England, Scotland, Wales, Northern Ireland and Ireland. Distances, ascent, typical time, trailhead coordinates and points of interest are approximate, compiled from public route guides. Northern Ireland routes (Mournes, Causeway Coast, Belfast Hills, Antrim, Fermanagh) are well represented. User accounts, reviews, helpful votes, favourites and completed-hike logs are generated by `seed/build_dataset.py` with a fixed random seed, so every load is identical. Ratings are weighted by difficulty and review conditions follow the season hiked, so the aggregations produce meaningful results.

The data is deliberately varied:

- string, integer, float, boolean and date fields
- string arrays (`tags`, `best_seasons`)
- a nested object (`features`)
- GeoJSON points
- two embedded sub-document collections per trail
- an embedded log in each user

## 2. Data model

### `trails`
```json
{
  "_id": ObjectId,
  "name": "Slieve Donard via the Glen River",
  "description": "...",
  "region": "Mourne Mountains", "country": "Northern Ireland",
  "location": { "type": "Point", "coordinates": [-5.892, 54.2108] },
  "distance_km": 9.0, "elevation_gain_m": 850, "estimated_duration_mins": 300,
  "difficulty": "hard", "route_type": "out-and-back",
  "tags": ["summit", "forest", "river"], "best_seasons": ["spring", "summer", "autumn"],
  "features": { "dog_friendly": true, "wheelchair_accessible": false, "parking": true,
                "public_transport": true, "toilets": true, "cafe": true },
  "avg_rating": 4.0, "review_count": 7,
  "reviews": [ { "_id", "user_id", "username", "rating", "title", "comment", "hiked_on",
                 "conditions", "helpful_votes": [ObjectId], "created_at", "updated_at" } ],
  "points_of_interest": [ { "_id", "name", "type", "location": GeoJSON, "km_from_start",
                            "description", "created_at" } ],
  "created_by": ObjectId, "created_at": Date, "updated_at": Date
}
```

### `users`
```json
{ "_id", "username", "email", "name", "password": "<bcrypt hash>", "admin": false,
  "favourites": [ObjectId], "completed": [ { "_id", "trail_id", "completed_on", "duration_mins", "logged_at" } ],
  "created_at" }
```

### `blacklist`
`{ "jti", "user_id", "expires_at" }`: revoked JWTs. A TTL index deletes each entry when the token would have expired anyway.

### Embedding vs. referencing

| Relationship | Choice | Reasoning |
|---|---|---|
| Trail → reviews | Embedded | Reviews are always read in the context of one trail. A trail has tens, not thousands, of reviews, so it stays well within the 16 MB document limit. Adding a review is one atomic update. |
| Trail → points of interest | Embedded | POIs belong to exactly one trail and are small and few. |
| User → favourites | Array of trail ids (reference) | Trails are shared and change independently, so copying them into users would go stale. `$lookup` joins them on read. |
| User → completed hikes | Embedded log, referencing trails | The log is private to the user and append-mostly; trail details are joined on read. |
| Review → user | `user_id` reference plus a copied `username` | Showing a review never needs a join. The username is the only copied field, and it can't be changed after registration. |

**Alternative considered:** a separate `reviews` collection. It would scale better for very popular trails and make "all reviews by a user" queries cheaper. The cost would be a join or second query for every trail page and losing single-document atomicity. At this dataset size, embedding is simpler and faster. `avg_rating` and `review_count` are stored on the trail (denormalised) so list views can sort and filter by rating without unwinding reviews. They are recalculated by an aggregation after every review change (`refresh_rating`).

### Indexes (`trailblazer/db.py`)

| Index | Purpose |
|---|---|
| `trails.location` `2dsphere` | Required by `$geoNear` |
| `trails.region + difficulty` | Common filter combination |
| `trails.avg_rating` | Sorting by rating and the top-rated query |
| `users.username`, `users.email` (unique) | Fast login; the database itself enforces uniqueness |
| `blacklist.expires_at` (TTL), `blacklist.jti` (unique) | Self-cleaning revocation list |

## 3. Database operations

**CRUD.** Full create, read, update and delete on top-level trails and users, and on the `reviews`, `points_of_interest`, `favourites` and `completed` arrays.

Notable techniques:

- **Atomic "one review per user":** `update_one({"_id": trail, "reviews.user_id": {"$ne": me}}, {"$push": ...})`. The filter fails to match if the user has already reviewed, so two simultaneous requests cannot both succeed.
- **Positional updates:** `reviews.$.rating` changes one array element in place, and `reviews.$[].helpful_votes` removes a deleted user's votes from every review.
- **`$elemMatch` projection** returns one review without sending the whole array.
- **`$slice` projection** returns only the 3 latest reviews on the trail detail endpoint.
- **`$addToSet`** for helpful votes and favourites gives duplicate-free sets even under concurrency.
- **Cascade clean-up:** deleting a trail `$pull`s it from every user's favourites and log. Deleting a user removes their reviews and votes, then recalculates ratings.

**Complex queries.**

- **Filtering:** `build_trail_filter()` turns more than 20 query parameters into one MongoDB filter. It combines:
  - `$in` (any difficulty), `$all` (all tags or seasons)
  - `$gte`/`$lte` ranges
  - dotted-path boolean matches (`features.dog_friendly`)
  - an escaped, case-insensitive `$regex` across three fields with `$or`
- **Geospatial:** `$geoNear` (spherical, metres) returns trails nearest a point, with distance computed by the database. The same pipeline finds trails near a trail, excluding itself.
- **Pagination:** `skip`/`limit` with `count_documents`. `_id` is a secondary sort key so pages never overlap or skip items.
- **Aggregation pipelines:**

  | Endpoint | Stages |
  |---|---|
  | Review listing | `$unwind` → `$replaceRoot` → `$addFields` (`$size`) → `$sort` → `$facet` (count and page in one round trip) |
  | Favourites, completed log, personal stats | `$lookup` joins |
  | Regions, difficulty, tags | `$group` with `$avg`/`$sum`/`$max`/`$addToSet`/`$first`, `$cond` |
  | Distance histogram | `$bucket` |
  | Monthly reviews | `$year`/`$month` date operators |

**Alternatives.**

- MongoDB `$text` search would rank results by relevance, but it requires a text index and doesn't match partial words. Escaped regex is predictable for short name searches.
- Range-based (keyset) pagination would beat `skip` on very large collections. `skip` is fine for hundreds of documents and lets clients jump to any page.

## 4. API design

- **Structure:** follows the Biz Directory layout from the module: one Flask **Blueprint** per resource in its own folder (`blueprints/trails/trails.py`, `blueprints/reviews/reviews.py`, ...), with access control in `decorators.py`. Two changes from the module layout:
  - An application factory (`create_app`) replaces the module-level `app`/`db` globals. The database is passed in, so the tests can point the same code at a separate test database.
  - Validation, error handling and pagination live in shared modules rather than being repeated in each route.
- **REST conventions:**
  - Nouns for resources, with sub-documents nested under their parent (`/trails/{id}/reviews/{review_id}`).
  - `GET`/`POST`/`PUT`/`PATCH`/`DELETE` used for their proper meanings. PUT needs every required field; PATCH accepts any subset.
  - Favourites use `PUT` because adding one is idempotent: `201` the first time, `200` after.
  - Status codes: `201` with a `Location` header on create, `204` on delete, `400` validation, `401` unauthenticated, `403` forbidden, `404` missing or invalid id, `405` wrong method, `409` conflict, `415` unsupported body format.
  - Errors are always JSON (`{"error": ...}` as in BE04); Flask's HTML error pages are replaced.
  - As in BE03 Table 3.2, a malformed id is treated the same as an unknown one: **404** with a message such as "Invalid trail ID", never a server error.
  - Missing or invalid input returns **400** "Validation failed", with a `details` object naming each field. The BE04 examples return 404 "Missing form data"; 400 is used here because the URL was found and only the submitted data was wrong.
- **Request bodies:** read with `request.form` from `x-www-form-urlencoded` or form-data, exactly as in BE03/BE04 and the Postman demonstrations. JSON is also accepted, so other front ends (e.g. an Angular app) can post JSON. Form values are always strings, so `form_to_payload()` converts them to the schema's types:
  - numbers and booleans are converted from text
  - comma-separated text becomes a list
  - `latitude`/`longitude` become a GeoJSON point
  - feature flags become the `features` object
- **Validation:** `validation.py` uses a small declarative `Field`/schema system rather than repeated `if` checks. It handles:
  - type checks (it rejects `true` where a number is expected, which Python would otherwise accept because `bool` is a subclass of `int`)
  - ranges, lengths, enumerations, regex formats, URLs, de-duplicated lowercase tag arrays
  - non-future dates
  - latitude/longitude bounds, converted to GeoJSON (`[lng, lat]` order)
  - rejection of unknown fields

  Every error is reported at once, so a client can fix a form in one go. Query-string values are validated just as strictly.
- **Serialisation:** a custom `JSONProvider` converts `ObjectId` to strings and dates to ISO 8601. This means documents can be returned directly instead of being converted field by field.

## 5. Authentication and authorisation

- Passwords are hashed with **bcrypt** (salted and deliberately slow). Login gives the same error for an unknown user and a wrong password, to prevent account enumeration.
- Login returns a **JWT (HS256)** containing the user id, username, admin flag, expiry and a unique `jti`.
- `@jwt_required` checks four things:
  - the signature and expiry
  - that the token isn't on the blacklist
  - that the user still exists, so deleting an account cuts off its tokens at once
- `@admin_required` builds on `@jwt_required`.
- **Ownership rules:**
  - Only a trail's creator or an admin may edit the trail or its POIs.
  - Only a review's author may edit it; the author or an admin may delete it.
  - Users can't vote on their own reviews.
  - Changing email or password requires the current password.
- Logout stores the token's `jti` in `blacklist` with a TTL index, so the table never grows without limit.

## 6. Testing

- **pytest** (`tests/`, 59 tests) runs against a separate `trailblazer_test` database, seeded at start and dropped at the end. It covers:
  - happy paths, plus validation, authorisation, not-found and conflict cases
  - pagination, filters and sorting
  - geo queries
  - rating recalculation
  - cascade deletes
  - every stats endpoint
- **Postman** (`postman/TrailBlazer.postman_collection.json`, 68 requests, 142 assertions) runs end-to-end in order:
  1. registers a fresh user and logs in
  2. creates a trail, POI and review
  3. checks the trail's derived rating
  4. tests error cases
  5. deletes everything it created

  This makes the run repeatable. Collection variables pass ids and tokens between requests. The collection is generated by `postman/build_collection.py`, so it stays in sync with the code.

## 7. Possible extensions

- Store each route as a GeoJSON `LineString` and use `$geoIntersects` (e.g. "trails passing through this national park polygon").
- Image upload for reviews, and refresh tokens.
- Rate-limiting the login endpoint.
- Move reviews into their own collection if individual trails start receiving thousands of reviews.
